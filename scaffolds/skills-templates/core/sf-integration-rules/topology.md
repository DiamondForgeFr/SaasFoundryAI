# Topology grammar — monorepo vs multirepo

> **Status: stub.** Filled by Story #309 (S4 — mono vs multi divergence). Until that story lands, fall back to reading `.saasfoundry.json` (`structure: monorepo | multirepo`) and the package READMEs
> under `packages/` (monorepo only).

## Detect topology (anchor)

- On-disk signal: `packages/` exists at the repo root → **monorepo**. Otherwise **multirepo**.
- Manifest signal: `.saasfoundry.json` → `structure` is the source of truth.
- CLI signal: `sf status --claude-friendly --no-network` prints the structure on the `project:` line.

## Mono vs multi — where shared code lives (anchor)

| Concern                  | Monorepo                                                            | Multirepo                                                  |
| ------------------------ | ------------------------------------------------------------------- | ---------------------------------------------------------- |
| TypeScript types         | `packages/shared-types` (canonical) + vendored mirror per app       | Vendored mirror per app — no canonical workspace           |
| Zod validation           | `packages/shared-validation` (canonical) + vendored mirror per app  | Vendored mirror per app — no canonical workspace           |
| Runtime constants        | `packages/shared-config` (mono-only — no vendored mirror)           | Inlined per app (drift-guard parity assertions)            |
| UI primitives            | `packages/ui-primitives` (source-only, imported via `@<project>/…`) | Vendored shadcn under `apps/web/src/components/ui/shadcn/` |
| API client (typed hooks) | `packages/api-client` (auto-generated by orval from `apps/api` OAS) | Hand-written hooks under `apps/web/src/hooks/api/`         |

## Module-deposit pattern (mono only) (anchor)

Some installers (`storage`, `email`) deposit files **directly** into `packages/shared-*` instead of vendoring mirrors. These deposits are:

- **Idempotent** — `sf update` won't duplicate them
- **Activation-gated** — only deposited when the module's consumer file is installed
- **Multi-aware** — multirepo keeps the same shape inlined per app, drift-guard parity assertions enforce it

| Module  | Mono deposit                            | Multi inlined location                            |
| ------- | --------------------------------------- | ------------------------------------------------- |
| storage | `packages/shared-config/src/storage.ts` | inlined in `apps/api/.../organization.controller` |
| email   | `packages/shared-types/src/email.ts`    | inlined in `apps/api/.../mailersend.service.ts`   |

## Drift discipline (anchor)

- `shared-types` and `shared-validation` ship as **canonical workspace + vendored mirror** in monorepos. **Edit all three copies in lockstep** (canonical + each app's mirror) — the drift-guard test
  will fail otherwise.
- Multirepo inlined literals must stay byte-identical with their monorepo counterparts when the same domain shape exists on both sides — this is what makes the same blueprint work for both topologies.
- **Do not disable a failing drift-guard test** — fix the divergence on both sides instead.

## Decide where new code goes (anchor)

When adding a new symbol, ask in order:

1. Runtime constant or threshold both apps must agree on? → `shared-config` (mono) / inlined per app (multi)
2. Zod schema validated identically on both sides? → `shared-validation` (factory pattern)
3. TypeScript type / interface / enum used on both sides? → `shared-types` (vendored if hand-written, deposited if module-scoped)
4. Headless UI building block? → `ui-primitives` (mono) / vendored shadcn (multi)
5. Backend endpoint? → `apps/api` then regenerate api-client (mono) / hand-write hook (multi)
6. Otherwise → app-specific, stays under `apps/<app>/src/`
