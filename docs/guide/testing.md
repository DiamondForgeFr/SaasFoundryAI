# Testing

SaaSFoundry's test strategy is layered: fast checks on every commit, slightly heavier checks on every push, full coverage on demand. Each layer has a specific job, and CI mirrors them so local success
maps to green pipelines.

This page covers the test layout for **the SaaSFoundry CLI itself**. Projects generated by `sf new` ship with their own Jest + Supertest setup for the NestJS API and Vitest + React Testing Library for
the Vite frontend — see the `apps/api/tests/` and `apps/web/tests/` folders in any generated project for that.

## The four layers

```text
┌───────────────────────────┐
│  test:pre-commit ~15s     │  format + lint + build + jest  (576 tests)
├───────────────────────────┤
│  test:pre-push   ~2–3 min │  test:docker --count 2          (top 2 scenarios)
├───────────────────────────┤
│  test:full       ~3 min   │  pre-commit + pre-push          (full local loop)
├───────────────────────────┤
│  test:docker     ~65 min  │  all 18 Docker build scenarios  (nightly / on demand)
└───────────────────────────┘
```

Every generated project — and the SaaSFoundry repo itself — uses Husky to wire `test:pre-commit` to the `pre-commit` hook and `test:pre-push` to the `pre-push` hook. You never have to remember to run
them.

## `test:pre-commit` — the fast loop

```bash
npm run test:pre-commit
```

Runs four things in sequence. If any step fails, the commit is blocked.

| Step           | Command                  | Why                                                                                                                   |
| -------------- | ------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| **Format**     | `prettier --write`       | Rewrites files in place. The first run after a commit often reflows something — expect a follow-up `style()` commit.  |
| **Lint**       | `eslint`                 | Flat config in `eslint.config.mjs`. No `any`, no unused imports, no `// eslint-disable-next-line` in shipped code.    |
| **Type-check** | `tsc`                    | Strict mode, `noEmit` under the hood (the `build` script is what runs).                                               |
| **Jest**       | `jest --passWithNoTests` | Runs the four Jest projects (`unit`, `integration`, `e2e`, `smoke`) defined in `jest.config.js`. Currently 576 tests. |

Total time on a warm cache: ~15 seconds. If it takes longer than 30 seconds something is off — usually a stale `dist/` directory or a node_modules mismatch.

### The four Jest projects

`jest.config.js` splits tests into four named projects so you can run exactly the suite you care about:

```bash
npm run test:unit         # fast, isolated: parse trees, pure functions, regex handling
npm run test:integration  # spins builders + installers against a temp dir
npm run test:e2e          # invokes the compiled CLI end-to-end on a temp dir
npm run test:smoke        # runs sf new once and greps the output
```

- **`unit`** — no filesystem, no subprocesses. Anything in `src/__tests__/unit/`.
- **`integration`** — scaffolds into a temp dir using real builders + installers but without spawning `npm install`. 30 s timeout.
- **`e2e`** — runs the compiled `bin/sf.js` with a child process. 60 s timeout.
- **`smoke`** — one full `sf new` + file-structure assertions. 120 s timeout.

All four run under `test:pre-commit`, but in CI you can parallelise them via `--selectProjects`.

## `test:pre-push` — the real-build loop

```bash
npm run test:pre-push
```

Delegates to `test:docker -- --count 2` — it generates two real projects inside Docker (multirepo-minimal + monorepo-minimal), runs `npm install`, `prisma generate`, `nest build`, `vite build`, and
asserts the resulting bundle has the expected shape.

~2–3 minutes on a warm cache (the Dockerfile bakes the CLI source in, so only the npm installs vary). This is the last line of defence before your changes hit a remote branch.

Why two scenarios and not the full suite? Because the full suite is 65 minutes. Top-2 is the minimal real-build signal — if those two fail, something is structurally wrong. The remaining 20 scenarios
exercise module permutations; they belong in nightly CI, not pre-push.

### Opting out

For branches prefixed `rc-*`, the pre-push hook also runs automatic version management (`scripts/tag-manager.sh`). For regular branches you get Docker tests only. If you need to push a truly urgent
fix and want to skip pre-push, `git push --no-verify` exists — but reach for it only when the alternative is worse than the risk.

## `test:full` — what CI runs per PR

```bash
npm run test:full
```

Alias: `test:pre-commit && test:pre-push`. The full local signal. GitHub Actions runs exactly this on every PR.

## `test:docker` — the 18-scenario build matrix

```bash
npm run test:docker               # all 18 scenarios   (~65 min)
npm run test:docker -- --count 5  # top 5 by priority  (~10 min)
npm run test:docker:scenario monorepo-full-modules
npm run test:docker:list
```

Each scenario is an entry in `tests/docker/scenarios.ts`. Three scenario types exist:

| Type           | What it does                                                                          |
| -------------- | ------------------------------------------------------------------------------------- |
| **generation** | `sf new` with specific flags, then `npm install` + `nest build` + `vite build`        |
| **update**     | Generate a minimal project, then `sf update --add-modules <...>`, then rebuild        |
| **ai**         | Generate a project and assert on `.claude/skills/` + `CLAUDE.md` structure (no build) |

Scenarios are ordered by priority in `ALL_SCENARIOS` so `--count N` runs the N most important ones. Priority rationale is documented inline in the file:

- 1–2: minimal builds (catch fundamental breakage fast)
- 3–4: full builds (all modules combined)
- 5–6: update flows
- 7–9: AI config (structural, no build — fast)
- 10–12: single module variations
- 13–14: module combos
- 15–16: monorepo module combos
- 17–18: remaining update flows

Run `npm run test:docker:list` to see the full list with priority order at any time.

### Why Docker?

Because generation writes files and mutates a live `node_modules` tree. Running 18 scenarios in the host environment pollutes the repo's own deps and fights with the cached CLI build. Docker gives
each scenario a clean Node 20 image with the CLI source baked in — same tree every time, nothing leaks across scenarios.

The image is built once (`Dockerfile.test`), then each scenario runs in a fresh container. On a warm cache the image build is ~1 second, so the overhead is negligible.

## Writing a new scenario

To add a generation test, edit `tests/docker/scenarios.ts`:

```typescript
{
  type: 'generation',
  name: 'my-new-scenario',
  projectName: 'my-proj',
  isMonorepo: false,
  dbSetup: 'manual',
  s3Setup: 'manual',
  emailService: 'mailersend',
  includeAnalytics: true
}
```

Insert it at the priority you want (position in the array). Then:

```bash
npm run test:docker -- --scenario my-new-scenario
```

Iterate until green, then commit. The next `test:pre-push` run will still only execute the top 2 by default — your new scenario only joins the pre-push set if you move it into the top 2 by priority.

For `update` scenarios, the assertion model is "generate minimal → add modules → still builds". For `ai` scenarios, the assertion model is purely structural (`.claude/skills/sf-workflow/SKILL.md`
exists, `CLAUDE.md` has the workflow section, etc.).

## Coverage

Coverage runs through Jest's built-in collector. Configuration in `jest.config.js` under `collectCoverageFrom`:

- Includes all of `src/**/*.ts`
- Excludes declarations, spec files, the test harness
- Excludes interactive-only code: `src/runners/**`, `src/index.ts`, `src/commands/new.ts|tools.ts|workflow.ts`, interactive prompt files

That exclusion list exists because those files are covered by the E2E Docker scenarios, not by Jest. Counting them twice would dilute the coverage signal.

To produce a coverage report locally:

```bash
npm test -- --coverage
open coverage/lcov-report/index.html
```

## What each layer catches (and what it doesn't)

| If you want to catch…                               | You need…                                                  |
| --------------------------------------------------- | ---------------------------------------------------------- |
| A type error, a missing import, a lint violation    | `test:pre-commit`                                          |
| A regression in pure CLI logic (parsing, manifest)  | `test:pre-commit` (it runs all 4 Jest projects)            |
| A broken template (e.g. malformed `package.json`)   | `test:pre-push` (Docker scenarios install & build)         |
| A broken overlay combo (email + storage + monorepo) | `test:docker --count N` covering that combo                |
| A broken scaffolded test file                       | Smoke-generate locally and run `npm test` inside the proj  |
| A broken Husky hook generated into the project      | Generate and attempt a commit inside the generated project |

The last two rows are the weak spots: if you touch scaffolded tests or scaffolded hooks, nothing in the local test suite will tell you they're broken — you need to smoke-generate and poke them
manually. Those are precisely the kinds of changes we eventually want new Docker scenarios for.

## Debugging a failing test

A few patterns that come up often:

- **Flaky smoke test** — usually a port collision on the generated project's health check. Bump the random-port generator in `tests/docker/assertions.ts`, not the test itself.
- **"Docker image missing" on pre-push** — `docker ps` to confirm Docker is running; the pre-push script fails fast if the daemon isn't up.
- **Integration test passes locally, fails in CI** — almost always a path-case bug (macOS is case-insensitive, Linux isn't). Grep for hard-coded file names with mixed case.
- **Jest says `Cannot find module`** — stale `dist/`. Run `rm -rf dist && npm run build` and retry.
